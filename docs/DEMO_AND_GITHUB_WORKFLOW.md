# Demo Flow and GitHub Conflict Guide

## Demo flow for a non-technical user

1. Start the site with `npm start`.
2. Open `http://127.0.0.1:3000/`.
3. Search `MSFT`.
4. Point out the short answer under `Why picked`.
5. Scroll to `Monthly Picks`.
6. Click `View report` on any pick.
7. Scroll to `Model Portfolio` and explain that previous picks can be held, upgraded, downgraded, or removed.
8. Scroll to `Risk Feed` and explain that news/geopolitical items are interpreted by impact, not just displayed as headlines.


## Does the user manually enter tickers?

There are two different modes:

### Current MVP mode

The demo uses manually defined sample stocks in `src/app.js`. This lets the UI work immediately without needing paid data APIs.

### Future production mode

The real screener should automatically find monthly picks. Users should not need to manually enter every ticker. The system should scan a predefined universe, score each stock, filter out red flags, rank the best candidates, and then publish the monthly picks.

A user can still search a ticker manually, but monthly picks should be generated by the platform.


## How many stocks should production screen?

Production should screen as many stocks as the data provider, budget, and performance limits allow. The best approach is broad scanning plus strict eligibility filters.

A practical rollout is:

1. Start with a trusted index universe, like S&P 500 or Nifty 500.
2. Expand to large and mid caps.
3. Expand to all major-exchange listed stocks.
4. Add global stocks after data normalization is reliable.
5. Treat small caps and microcaps as a separate high-risk mode.

The monthly picks should come from the eligible ranked universe, not from manually selected tickers.

## Example: changing one pick safely

Suppose you want to change Microsoft's short reason.

1. Pull latest code first:

```bash
git pull --rebase origin main
```

2. Open `src/app.js` and find:

```js
ticker: "MSFT"
```

3. Change only the `whyPicked` field.

4. Validate:

```bash
npm run validate
```

5. Commit and push:

```bash
git add src/app.js
git commit -m "Update MSFT pick reason"
git push origin main
```

## Will every future push create conflicts?

No. Pushing again does not automatically create conflicts.

Conflicts usually happen only when:

- You changed a line locally, and the same line changed on GitHub before you pushed.
- Two people edited the same section of the same file.
- You edited files on GitHub web UI and locally without pulling first.

## What to do if Git says there is a conflict

1. Do not panic.
2. Open the conflicted file.
3. Look for conflict markers:

```text
<<<<<<< HEAD
Your local version
=======
GitHub/remote version
>>>>>>> branch-name
```

4. Keep the correct final version and remove the markers.
5. Run validation.
6. Continue the rebase or merge.

For a rebase conflict:

```bash
git add conflicted-file
git rebase --continue
```

Then push:

```bash
git push origin main
```

## Best next improvement to reduce conflicts

Move the mock stock data out of `src/app.js` into separate files under `src/data/`. This lets one person update monthly picks while another person changes UI behavior.
