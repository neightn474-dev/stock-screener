# Demo Flow and GitHub Conflict Guide

## Demo flow for a non-technical user

1. Start the site with `npm start`.
2. Open `http://127.0.0.1:3000/`.
3. Search `RELIANCE.NS` or `NIFTYBEES.NS`.
4. Point out the short answer under `Why picked`.
5. Scroll to `Monthly Picks`.
6. Click `View report` on any pick.
7. Scroll to `Model Portfolio` and explain that previous picks can be held, upgraded, downgraded, or removed.
8. Scroll to `Risk Feed` and explain that news/geopolitical items are interpreted by impact, not just displayed as headlines.


## Does the user manually enter tickers?

There are two different modes:

### Current MVP mode

The demo uses local Indian stock and ETF samples in `src/app.js`, but the screener now automatically scores, filters, ranks, and publishes monthly picks from that sample universe.

### Future production mode

The real screener should automatically find monthly Indian stock and ETF picks. Users should not need to manually enter every ticker. The system should scan a predefined Indian universe, score each stock/ETF, filter out red flags, rank the best candidates, and then publish the monthly picks.

A user can still search an Indian ticker manually, but monthly picks should be generated by the platform.


## How many stocks should production screen?

Production should screen as many Indian stocks and ETFs as the data provider, budget, and performance limits allow. The best approach is broad scanning plus strict eligibility filters.

A practical rollout is:

1. Start with trusted Indian index universes, like Nifty 50, Nifty Next 50, and Nifty 500.
2. Expand to Indian large and mid caps.
3. Expand to NSE/BSE listed stocks and Indian ETFs.
4. Add sector/factor/thematic Indian ETFs after data normalization is reliable.
5. Treat Indian small caps and microcaps as a separate high-risk mode.

The monthly picks should come from the eligible ranked universe, not from manually selected tickers.


## Criteria that are working in the static site

The static site now checks the core criteria in browser-side JavaScript:

- India-only stock and ETF sample universe
- Weighted advisor score
- Liquidity threshold
- Data-quality threshold
- Red-flag filtering
- Sector concentration limit
- At least one ETF in monthly picks when eligible
- Short reason, main risk, and removal trigger for each pick

This is still not live market data. The next production step is connecting the same engine to NSE/BSE stock and ETF data APIs.

## Example: changing one pick safely

Suppose you want to change Reliance’s short reason.

1. Pull latest code first:

```bash
git pull --rebase origin main
```

2. Open `src/app.js` and find:

```js
ticker: "RELIANCE.NS"
```

3. Change only the `whyPicked` field.

4. Validate:

```bash
npm run validate
```

5. Commit and push:

```bash
git add src/app.js
git commit -m "Update Reliance pick reason"
git push origin main
```




## Why project docs are not in root README

The root `README.md` was removed from this PR to avoid a GitHub add/add merge conflict with the repository's existing `README.md` on `main`. AdvisorIQ-specific project documentation now lives in:

```text
docs/ADVISORIQ_README.md
```

This keeps the new screener work conflict-free while preserving the full setup, preview, validation, and workflow notes.

## Fresh PR when the old one has conflicts

If GitHub says the old pull request has conflicts, close that PR and open a new one from the latest clean branch. Before opening the new PR, run:

```bash
npm run validate
```

The validator now scans every project text file, including docs, HTML, CSS, JavaScript, JSON, and Markdown, and fails if conflict markers are present anywhere. This means you do not have to manually inspect every file for merge markers before creating the new PR.

Suggested flow:

```bash
git status
npm run validate
git add .
git commit -m "Your change"
git push origin your-branch
```

Then open a fresh PR from that pushed branch.

## Preview before pushing

If you want to check the website before pushing to GitHub, run:

```bash
npm run preview
```

Then open:

```text
http://127.0.0.1:4173/
```

This lets you preview the working Indian screener locally, confirm the monthly picks render correctly, and avoid pushing broken conflict-marker text.

## Will every future push create conflicts?

No. Pushing again does not automatically create conflicts.

Conflicts usually happen only when:

- You changed a line locally, and the same line changed on GitHub before you pushed.
- Two people edited the same section of the same file.
- You edited files on GitHub web UI and locally without pulling first.

## What to do if Git says there is a conflict

1. Do not panic.
2. Open the conflicted file.
3. Look for conflict markers:

```text
START CONFLICT MARKER: your local version
SEPARATOR MARKER: incoming GitHub/remote version
END CONFLICT MARKER: branch name
```

4. Keep the correct final version and remove the markers.
5. Run validation.
6. Continue the rebase or merge.

For a rebase conflict:

```bash
git add conflicted-file
git rebase --continue
```

Then push:

```bash
git push origin main
```
